### 8.5 全身面板「平度审计」与框架级修复（1.1.13）

在脸上确诊的「画了等于没画」不是孤立问题 —— 那套影色常量是**全贴图共用**的。新写
`tools/bride_panel_audit.py` 做机械化审计：按画家+尺寸分组，算每块面板内像素两两色距的**最大值
`span`**（含 alpha 通道），`span < 14` 即整块读成死色。结果分三类：

| 类别 | 实测 | 处置 |
|---|---|---|
| **真缺陷：色距上限不够** | `SKIN_SH (233,227,239)` 与 `SKIN (246,236,247)` 色距上限只有 **13**，alpha 开到 1.0 都到不了可辨阈 ⇒ `p_skin` 的体表渐变（手/腿/颈的底）、手部"指缝"、锁骨阴影全是死的 | 体表渐变改收在 `SKIN_COOL`（距 `SKIN_HI` 48）；手部改成按行给可读体块；锁骨改成贴上缘的浅影（旧版是半径算错、会画到缎面上的 disc） |
| **真缺陷：框架原语退化** | `Rect.vgrad` 的 `f = yy/max(1,h-1)` 在 **h==1 的面板上恒为 0** ⇒ 整条只落第一档。发冠 7x1、项圈 5x1、发簪 9x1、腰带、蝴蝶结、袜口全是 1 行高 ⇒ 整条死色（实测发冠整条 `#E8F6FF`） | `vgrad` 增加 h==1 分支：把同一对颜色改沿**长度**铺开（金属/缎面反光）。一处修复覆盖发冠/项圈/发簪/袜口等全部 1 行面板 |
| **设计如此（不动）** | `sole` 平色鞋底、`hem_lLace` 等**专门给蕾丝边条的 1px 面板**、1×1 面板（gem/hand/heel 等，物理上装不下明暗）、`veil_lace 10x1` 顶边实白 | 保留 |

审计工具的两个坑（都已在代码注释里写明）：
1. **面板归属**：图集里多条模型面**共享同一矩形**，`main()` 按清单顺序作画 ⇒ 同一矩形**最后画的
   那条才算数**；按清单条目直接归类会把归属记错，看到一堆莫名其妙的死色面板。
2. **必须含 alpha**：蕾丝/薄纱是「白网 + a=0 镂空」，RGB 本来就该是一色，只看 RGB 会把面纱误判成死色。

### 8.7 面纱：刚性板 → 4 段真骨骼布料链（1.1.14）

原来面纱是**一整块刚性板**（单骨 `veil` + 2 个 slab），任何动作都只能整幅硬甩。三个层次的问题都修了：

| # | 问题 | 实证 | 修法 |
|---|---|---|---|
| ① | **只有一根骨**，布没有形变 | 全 9 个含面纱的剪辑都只写 `veil` 一根 | 拆成 `veil → veil2 → veil3 → veil4` 链，**每段 pivot 落在自己上缘**（= 铰链）；根骨 pivot 保持 `(0,30.8,4.4)` 不动 ⇒ 已调好的旧键全部继续成立 |
| ② | **朝外那面被送给内衬** | 4 块 slab 写的是 `hidden="nsu"` ⇒ 朝内的 n 与**朝外的 s** 都被映射到共享 `@lining` 2×2 补丁（`LINING #9B9CB5` 灰蓝），整幅布朝观众的面只采一块 2×2 色块；蕾丝画笔只落在 1~4px 侧边条上。同项目所有布料（`hair_fall`/`train`/`sole`/`heel`）用的都是 `hidden="nu"` —— 面纱多了个 `s` | 改 `hidden="nu"`：内衬只留朝内的 n 与顶边 u，朝外的 s 交还蕾丝画笔。**覆盖层镂空孔 43 → 55 px**，面纱这才真是镂空白纱 |
| ③ | **窄条网眼全镂空** | 侧边/厚度面只有 1~2px 宽，`xx % 4 != 0` 对 1px 宽恒为假 ⇒ 整块 a=0（轮廓上能看穿的缝） | `p_veil` 增加窄条分支（`min(w,h) <= 2`）铺半透明白纱；并新增 `band=2`「纯网格、不带压边」档给中间两段（否则四段各长一圈花边） |

**动画**：新增 `chain()` / `chain_oneshot()` / `veil_chain()`。根段沿用原键（动画师按旧版调过的量不动），

## 9. 裙摆拆链（**1.1.18 已实施**）

布料链从五条扩到八条：面纱 4 段、长发 3 段、鬓发左右各 2 段、拖尾 2 段，**外加裙摆前后/左/右三组各 3 层**。

### 9.1 结构（为什么不是"把板往下挪"）

裙摆的板**按左右分**，而每根骨又**横跨全部三层环**：

| 骨 | pivot | 板 | 面板高度层 |
|---|---|---|---|
| `skirt` | (0, 12.6, 0) | 6（前/后 n,s） | 9.8~13.2 / 7.6~10.0 / 6.9~7.8 |
| `hem_l` / `hem_r` | (∓4.6, 9.4, 0) | 各 9（w,fw,bw / e,fe,be） | 同上三层 |

所以**不是**改板归属，而是**在每根根骨下面串两段子骨**，把中环/蕾丝两层环的板移下去：

```
skirt(12.6) → skirt2(10.0) → skirt3(7.8)     hem_r(9.4) → hem_r2(10.0) → hem_r3(7.8)     左右同理
  ↑ 上环                                        ↑ 上环
```
铰链取「下层环的上缘」（10.0 / 7.8）= 两层环的交叠处。**根骨的名字、pivot、旧键一律不动** ⇒
现有 **27 个 (剪辑, 根骨) 对**（9 个剪辑 × skirt/hem_r/hem_l，含 `skill_consort` 的两侧 30° 独立侧掀、
`skill_veil_snare` 的 30° + 22°/z12°）**语义完全不变**，链只往下长。

### 9.2 等价性怎么证的（关键）

换父骨之所以等价，是因为骨骼继承的数学保证「子骨零旋转时，板的世界位置与父骨直接持有完全一致」。
但这靠推理不够，我写了 `tools/bride_skirt_check.py` **把它数出来**：

- 对裙摆族全部体块的 8 个角点、10 个剪辑 × 24 帧算世界坐标，存基线后比对。
- **键里绝不能带骨名**（改造就是要换父骨）⇒ 用**体块自身的 `origin+size` 做身份**，这样"同一块板换了骨"仍对得上。
- 结果：**第一步（只换父骨、不动键）0 偏差、49920 个角点逐块逐帧完全一致**；
  第二步（改链后）**上环 0.000000u**（旧键语义分毫未动），中环/蕾丝按设计出现滞后。

### 9.4 踩坑：**空判通过**

第一版分组统计里我把 `size[1]` 当成了顶面 y（应为 `origin_y + size_y`），于是三层全落进同一分组，

## 10. 子段幅度包络：从几何改造转入动画曲线（**1.1.19 已实施**）

八条布料链此前只有「幅度 ×scale + 固定相位」——每一段全程一个倍率、一个滞后，
读起来是"整段均匀地跟一下"。真实布料/头发的拖动**跟着速度走**：起手慢半拍、峰值处甩过头、
主体停下时它要收得比主体更早。本轮给**非循环剪辑**的子段加相位包络。

### 10.1 公式

```python
phase_env(keys, cycle, amp, rest_in, rest_out)   # 三段：起手 rest_in → 峰值 amp → 收尾 rest_out
amp_norm(keys)                                   # m(t) = |父骨(t)| / max|父骨|
chain_oneshot(..., env=penv, lag_env=lenv)       # nt = t + dt*(0.25 + 0.75*m(t))，再乘 env(t)
```

- **包络取「源时刻」**，不是平移后的时刻。第一版取平移后时刻，子段自己的峰值正好落到包络的衰减段上，
  实测末段峰值不升反降（`skill_bouquet/veil 2.16 → 1.65`）——"甩开大"完全没发生。改成源时刻后 +18%。
- **滞后也跟着收**：`lag_env = 0.25 + 0.75*m(t)`。只压幅度不压时间的话，末梢在**时间上**仍拖到最后，
  实测"归零相位"几乎不动（0.868 → 0.855，等于没做）。
- **循环剪辑不参与**（`c.loop` 直接跳过）：循环里没有"起手/收招"，且任何相位包络都会破坏首尾等值。

### 10.2 用什么量验收（换过一次指标）

| 指标 | 为什么不用 / 为什么用 |
|---|---|
| 末段峰值 | 用：`amp` 段的直接效果。49 行全部上升，合计 **+18.2%** |
| 「主体幅度<峰值10%的帧里子段平均」当残尾 | **不用**：这个窗口把起手段也算进去（那里主体同样安静），量出来的数几乎不随包络变化 |
| 最后 25% 时段的平均幅度 | **不用**：峰值抬高会把整段一起抬，测到的是"摆得更大"，不是"收得更早" |
| **归零相位**（末段最后一次超过自己峰值 10% 的时刻 ÷ 剪辑长度） | 用：对整体幅度**不变**，只反映时序。合计 49 行：**提前 34 / 不变 12 / 变晚 3**，均值 0.957 → 0.920 |

那 3 行"变晚"追到了根因、不是抖动：`skill_bouquet` 的裙摆根骨自己在 `1.4s: -12°` 之后 `1.45s: 0°`、
`1.7s` 又有一段 `-4°`（父骨自带第二段小回摆）。旧版子段滞后大，`1.7s` 那根键被映射到 1.97s **超出片尾被丢掉**，
所以子段早在 1.72s 就归零；滞后收窄后它落进片内（1.79s），子段于是忠实地跟了那个小回摆，
末梢残留 `0.75°`（父骨峰值 12° 的 6%）。这是"跟随"而不是"拖尾"。

### 10.3 时间映射必须强制单调（本轮踩的最大一个坑）

`nt = t + dt*lag(t)` 这个映射**不单调**：滞后倍率在回落段变化很快，而剪辑里常有相距 0.05s 的一对键
（`1.4s: -12°` 紧跟 `1.45s: 0°`）。只要滞后变化量超过键距，后一个键就被映射到**前一个键之前** ——
子段"先归零、再跳回去"，肉眼就是一次抽搐。

**实测**：这种「过近（<0.031s）又跳变（>20% 峰值）」的相邻键对，父骨 **0 对**、子骨 **44 对**（非循环）
＋45 对（循环）—— 也就是说这是本轮**引入**的缺陷，不是动画本身的风格。修法：

```python
nt = max(nt, prev + GAP)   # GAP = 0.02s，单调地板
```

`max()` 只在键过密时生效，正常间距下与朴素映射完全等价。**修后父骨 0 / 子骨 0。**

### 10.4 连带发现并修掉：生成器「缺轴填 0」

上面的抖动还有第二个来源，比时间映射更隐蔽：`Clip.to_json()` 原来是
`axes.get(a, {}).get(t, 0.0)` —— 一根骨在某个时刻只有 z 轴有键时，x/y 被**填 0**（而不是插值）。
旧代码里一根骨的三根轴**永远同刻**（同一个 dt 平移），所以这个 0 填得出来也看不出来；
本轮各轴按下标分别算滞后/包络，x 与 z 的抬键时刻不再重合，坑就露出来了。

改成线性插值后，全模型有 **70 个 (剪辑,骨) 条目 / 145 个「轴-键」点**的值被修正
（12 个 ≥10°、31 个 5~10°、63 个 1~5°、39 个 <1°），全部是"两个大键之间被填成 0"的假坑。
例：`skill_sacrifice.arm_r.z @2.1s` 旧 `0` → 新 `27.11`（相邻键是 `1.75s: 52°` 和 `2.2s: 20°`，
旧值等于让手臂在 0.45s 里 52°→0°→20° 抖一次）；`summon.crown.y @0.3s/@0.6s` 旧 `0` → 新 `17.33`。

**这改的是已验收动画的值**（观感会变），所以单独记一节。证据边界要说清：
裙摆根骨上 50 个改动点，**旧值全部恰好是 0.0** —— 证明改动来源是"填 0 坑"的修复，
包络没有泄进根段（`cloth_chain` 里根段走的是 `c.r(root, ch, keys)` 原始键，代码路径上就碰不到）。

### 10.6 更正前几轮的一处误归因：贴图其实每跑一次都不一样

前几轮（1.1.15 / 1.1.16 / 1.1.18）贴图哈希总在变，当时的解释是"面板写入顺序变了，
某条共享阴影的混合结果微调"。**这个解释是错的。**

真因在 `tools/bride_v2_skin.py` 的 `p_flat()` 里：`R.noise(..., hash(sample) & 0xFF, 0.10)`
—— 拿**内建 `hash()` 给字符串当噪声种子**。CPython 的 str hash 每个进程带随机盐
（PYTHONHASHSEED），所以**同一份输入、同一个生成器，每跑一次贴图都不一样**。实测：连跑三遍，
三个哈希（`890743c9…` / `2c24cad0…` / `5587f469…`）；加 `PYTHONHASHSEED=0` 复跑两遍则完全一致。
差异落在 `@lining` / `@cloth_dark` 这类**共享 2×2 补丁**上，每次 20~30 px —— 位置和数量都对得上
（用两个不同种子渲出 PNG 再逐像素 diff：**23 px**，全在 rect `[0,0,2,2]` / `[0,2,2,2]` 内）。

修法：`_stable_hash(s)`（只依赖字符与下标，跨进程稳定）。修后连跑三遍同哈希，贴图进 jar 才可复现。
**教训**：'渲染结果和上次不同'要先怀疑**随机性**，再怀疑顺序 —— `hash()` 用在字符串上就是随机数。

### 10.7 环状布链的验收判据：看**层间重叠**，不是中点间隙

`bride_chain_check.py` 的连续性判据是"上一段体块下缘中点 → 下一段上缘中点"的距离。
对**条状**布（面纱 / 长发 / 鬓发 / 拖尾）合适，对**同心层叠的环**不合适：裙摆每组骨横跨 9 块板，
层与层是**故意重叠**的（上环 y 9.8~13.2 / 中环 7.6~10.0，重叠 0.2u）。一圈环相对上一圈转过角度时，
中点距离必然大幅变化 —— 实测逐帧偏差 0.75~0.80u，于是 9 个剪辑全被标「不达标」，
但那是判据的错，不是裙摆裂了。

正解是量**竖直重叠量**：`overlap = max(下层顶点 y) − min(上层顶点 y)`，≥0 表示两层仍咬合，
负值才是裂口高度。工具 `tools/bride_seam_check.py`，全 10 个剪辑 × 3 组的结果：
**最小重叠恒为 +0.20u（= 静置设计值），裂缝 0**。也就是说摆到最大幅度时，层间咬合量一点没少
（铰链就在两层交叠面上，转动只让咬合更深）。

**规矩**：链条的"连续性"判据要按布的**几何类型**选 —— 条状看端点间隙，环状看层间重叠；
拿一种判据套所有链，会把设计当缺陷报出来。

### 10.8 曲线层面的审计：`tools/bride_chain_audit.py`

包络动的是**曲线**，几何全过不代表曲线没问题，所以另起一关，五条一起查（8 条链 × 10 个剪辑）：

| 项 | 内容 | 结果 |
|---|---|---|
| A | 收招归零：非循环剪辑每条链的根段+子段在 t=0 / t=length 三轴**恰好 0** | 0 问题 |
| B | 循环首尾等值：循环剪辑每个链通道端点数值**逐位相等** | 0 问题 |
| C | 键序单调 + **速度尖峰** | 0 问题 |
| D | 左右镜像：`hair_side_l*`↔`_r*`、`hem_l*`↔`hem_r*` 满足 `(x,-y,-z)` | 0 问题 |
| E | 链确实接上：非循环剪辑子段**键时刻**必须与根段不同（滞后 >0 的直接证据） | 0 问题 |

**C 项的判据换过一次 —— 值得记下来。** 初版写成"键距 < 15ms 就报"，实测报出 17 处，最小的
4ms 在 `skill_veil_snare.hem_l2`（1.147 / 1.151）。查值：`Δv` 只有 **0.01°** —— 那不是抽搐。
成因是三轴**各自**做滞后映射（各自有自己的 0.02s 单调地板），导出时再把三轴时间取**并集**、
缺轴按插值补齐（§10.4 那次修的 `at(ks,t)`），于是并集里必然出现"某一轴的真键 + 另一轴真键挤出的
插值点"这种 4ms 级伪键 —— 它的值就落在自己轴的分段曲线上，`lerp_mode` 是 `catmullrom` 时
切线估计几乎不变，删不删都一样。

真会抽搐的是**键距极小而 Δv 很大** = 速度尖峰（历史那 44 对就是：中间被插进一个 0，两侧 20°）。
判据改成：`Δt < 30ms` 且 `速率 > 5×该通道中位速率` 且 `|Δv| > 0.5°`。

**判据也要自测**：往 `skill_veil_snare.hem_l3` 注入一个 `t=1.198`、值 `0°` 的伪键（8ms 后），
复跑 —— C 项报 `速度尖峰 16.0×中位（Δt=8ms, Δv=2.15°）`，D 项同时报出"镜像最大偏差 2.162°"
（因为只注入了左侧）。**两个方向都能抓单侧异常**。审计器支持 `BRIDE_ANIM=<path>` 指向替身文件，
就是为这个自测准备的。

资源一个字节都没动 ⇒ **1.1.19 的 jar 仍是有效出货件**，不必重建。

## 12. `1.1.23`：召奬两条特性 + 「血纱」精修

### 12.1 召奬：有概率迅捷 + 静止缓慢回血

两条都落在召唤物自己（`CharmedZombie`），触发点在 `BrideZombie.summonMinion()` 的出口旁。

**迅捷（`BrideZombie.quickenMinion` → `CharmedZombie.makeSwift`）**

- 概率 `MINION_SWIFT_CHANCE = 0.30`（血月 `MINION_SWIFT_CHANCE_BLOOD = 0.50`，与持械概率同一套「血月加成」口径）。
- 加成 `SWIFT_SPEED_BONUS = 0.25`，走 `AttributeModifier(操作=MULTIPLY_BASE)`。**不用速度 buff**：
  buff 会到期、会被牛奶洗掉，而「这只跑得快」是它出生时抽到的成色，应当与它的存活期同寿命。
- 用 `addPermanentModifier` 而不是 `addTransientModifier`：召唤物 `setPersistenceRequired()` + `removeWhenFarAway(false)`，
  **跨存档存活**；transient 修饰符读档即丢，会出现「属性没了但标记还在」的半截状态。
- 视觉提示：出生瞬间脚下一撮 `CRIT`（与持械的 `ENCHANTED_HIT` 区分开），之后移动中每 10 tick 补一颗 ——
  玩家不必读 NBT 就能看出哪只先到。判定直接查属性修饰符（`isSwift()`），**不额外加同步字段**（属性值本来就同步）。

**静止回血（`CharmedZombie.tickIdleRegen`）**

- 「静止」判据 = `getDeltaMovement().horizontalDistanceSqr() < 1e-4 && onGround() && !isInWater()`。
  **按位移判而不是按「有没有目标」判**：召奬被打飞、或目标隔墙走不过来时它也站着不动，那些时候回血正是想要的效果。
- 连续静止 `IDLE_REGEN_DELAY = 40` tick 起效，此后每 `IDLE_REGEN_INTERVAL = 45` tick 回 `IDLE_REGEN_AMOUNT = 1.0` 点。
  慢到打不赢一场遭遇战，只够让活下来的召奬慢慢补齐。回血时撒原版心形粒子。
- **与「血纱回春」不是一回事**：`BLOOD_REGEN` 是美女僵尸自己的第 8 项技能，本轮这两条是**召唤物的出生特性**。

### 12.2 「更精致」怎么查：抠像素，而不是看渲染图

先看渲染图得到的第一印象（「裙摆像棋盘格」「头纱是一块白板」）**全是错的**，错在方法：

- 裙摆的「棋盘格」是**几何层次**（三层裙板交错 1u 重叠）配平光着色的读法，不是贴图问题 ——
  实测 `skirtA_n` 仅 18px 就有 18 色、邻域差 **31**，是整张图集里细节最足的区域之一。
- 头纱的「白板」是 **alpha 镂空**：面纱本来就是网格纱，透明像素占 30%~65%，
  把透明区算进「平坦度」当然得出「没画」。

于是新建 `tools/bride_patch_dump.py`：按图集清单逐面统计
**不透明像素数 / 覆盖率 / 不同颜色数 / 邻域差（相邻像素 RGB 差均值）**，且只统计 alpha>0 的邻域。
判据：邻域差 ≤2 约等于纯色、3~7 有渐变、≥8 有结构。

按这个口径，最平的大面**全是头纱的 `s` 面**（10×4px、4~6 色、邻域差 0.75~1.14），
而它们正是轮廓上最醒目的一块。同时暴露一个设计缺口：**这条「血纱」上一点血都没有**（不透明像素全是白）。

（工具本身踩过一个坑：`dump_grid` 的行号没加 `y0` 偏移，打印的是图集顶部空白行，
和统计函数的数字自相矛盾 —— 用独立探针复核后才定位到是打印端错、统计端对。**数字打架时先证伪工具**。）

### 13.2 三个关键取舍

1. **不新建骨骼，挂在 `veil4` 上**。新建一根「下摆骨」会让下摆在布料链甩动时**留在原地**（纱在动、边不动）。挂在链尾骨上，下摆自然跟着一起甩。
2. **下垂量取 0.4 / 1.2**。1px 级的起伏在渲染图里既看不出、数值上也测不到「波浪」；0.4/1.2 这组差值是侧影能读出圆头弧的最小搭配。整幅 9u 切 3 弧（每弧 = 18.75cm）是婚纱扇贝边的常见比例，再多就碎成锯齿。
3. **band=1**。`p_veil` 的底段档，本来就有「扇形花边 + 最重的血」，下摆接的正是那一段 —— 几何的扇贝与贴图的扇形花边对齐。

### 13.3 一个必须说清的局限：齿太细，撑不起蕾丝格

图集的**实际密度是 1.33 px/u**（不是各部件声明的 `tpu` —— 打包器全局压过一次）。所以：

| 面 | 尺寸 | 落到 `p_veil` 的分支 | 结果 |
|---|---|---|---|
| 齿的 s 面（正对背后视角） | 1×1 / 1×2 px | min(w,h) ≤ 2 ⇒ **窄条分支** | 半透明白纱（alpha 170~255） |
| 齿的 e/w/d 面 | 1×2 ~ 2×2 px | 同上 | 半透明白纱 |
| 对照：面板 `veil_low` 的 s 面 | 12×4 px | 正常分支 | 18 色蕾丝网 + 血渍 |

即：**下摆是一圈半透明薄纱流苏，不是带蕾丝图案的花边**。这符合蕾丝头纱边缘「越靠边越透」的直觉，但和上方 18 色蕾丝网存在质感落差。

若要把蕾丝图案也铺到下摆上，唯一的路是把齿做大到 **≥2.25u × 2.25u**（对应 3×3 px 才算得进正常分支）。代价：9u 幅宽只能切 4 弧、每弧下垂 ≥2u（占 `veil4` 本段 2.9u 的 69%），扇贝会变得很重。**本轮选择保留细齿 + 薄纱**。

### 13.4 验收（全部为数值判据，不看渲染图）

- 几何：骨骼 **49（未变）** / 体块 **140 → 149** / 面 **840 → 894**；seam 最差重叠 **+0.20u**、裂缝 **0**；链不达标 **0**。
- 生成器自校验 **1248/1248**；图集占用 30.79% → **31.27%**。
- **动画文件 sha256 逐位未变**（`25ee2b06…`，与 `1.1.20` 台账一致）⇒ 证明这次是纯几何改动、没碰动画。
- 图集登记：9 个部件 × 6 面 = **54 条**，`layer` 全为 `overlay`（登记进 `OVERLAY_PARTS` 生效，否则镂空会被强制不透明）。
- 穿模：下摆与其它部件**零深度重叠**；仅有的重叠是刻意的两处 —— 与面板的 0.20u 咬合、以及头纱压在背后长发上（0.25~0.36u³）。
- 贴图：9 条齿的每个面都有作画（无全透明空洞，不会露黑块）。

### 13.5 两个写错的判据（都栽在同一类问题上）

1. **在空集合上通过**：穿模检查原本按 `cube['name']` 过滤下摆 —— GeckoLib 导出的体块**不带 name**，于是候选集为 0，「深度穿模 0」是**零候选的假通过**。改成按几何签名认（头纱层的 z 起点 4.2、厚度 1.2、y0 < 19.6），并**先断言候选数 == 9** 再看结论。
2. **过度指定的签名**：出货脚本起初对**全模型**按 y 分桶数齿（期望 19.2 有 6 块、18.4 有 3 块），实际是 8 / 5 —— 裙摆和腿脚也有 y0 落在这些值的方块。断言必须限定在**下摆自己的层**里，并且断的是「9 块齿、6 短 3 长、最低点 18.4」这种意图，不是顺手捞到的数字。
