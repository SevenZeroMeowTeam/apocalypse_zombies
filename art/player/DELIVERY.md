# 玩家生命上限 100（`1.1.25`）

**需求原文**：「玩家血量为100」

## 做法

用**永久属性修饰符**把玩家生命上限顶到 100，而不是去改属性的基础值。

| 项 | 值 |
|---|---|
| 落点 | `event/CommonEvents.java`（登录事件已有，就在旁边加） |
| 配置键 | `specials.player_max_health`，默认 **100**，区间 **20 .. 1024** |
| 运算 | `AttributeModifier.Operation.ADDITION`，量 = `配置值 - 属性基础值` = **+80** |
| 修饰符 ID | 固定字面量 `7f4a2c81-9e35-4d6b-8c10-2a5e6b3f9d47` |
| 存续 | `addPermanentModifier`（进玩家 NBT，跨存档） |
| 挂钩 | `PlayerLoggedInEvent`（登录）+ `PlayerEvent.Clone`（死亡重生 / 换维度） |

### 三个设计取舍

1. **加修饰符，不改基础值**。基础值 20 是原版定的，别的模组和玩家自己的 `/attribute` 命令都会动它；摆成「基础值 + 这 80」两边互不打架，配置填回 **20 就等于关掉**这条改动。
2. **UUID 必须写死**。用 `UUID.randomUUID()` 的话每次登录换一个 ID ⇒ 永久修饰符一路叠加，进三次游戏血量 20 → 100 → 180。这是本条改动最狠的失效方式：**编译没有任何异常，多登几次才看得出来**。
3. **血量按比例换算，不无条件回满**。老存档 20/20 进新世界变 100/100；残血 8/20 只变成 40/100。无条件 `setHealth(getMaxHealth())` 等于每次进游戏白送一次治疗。

## 验收

`tools/check_player_health.py`（静态校验，exit 0）。它专盯这类**编译得过、上线才炸**的写法：

- 配置字段/键/默认值/区间存在且自洽（下界 ≤ 20 才能关掉，上界 ≥ 默认值）；
- 修饰符 ID 是 `UUID.fromString(...)`，**不是** `UUID.randomUUID()`；
- 运算是 `ADDITION`（`MULTIPLY` 会在已乘过的值上再乘，第二层登录就 500）；
- 用 `addPermanentModifier`（transient 存不进玩家 NBT，每次读档重套）；
- 差值由「配置值 − 属性基础值」算出，不硬编码 80；
- 登录 + Clone 两条链都挂了，且 Clone 处理器带 `@SubscribeEvent`；
- 血量按比例换算，没有 `setHealth(getMaxHealth())`；
- **`CommonEvents.class` 确实注册在 `EVENT_BUS` 上**（注册处：`ApocalypseZombies.java`）——
  漏了这一步，所有 `@SubscribeEvent` 都是死代码，配置改了没反应且日志不报错。

编译 `BUILD SUCCESSFUL`（12s，仅工程既有的过时告警）。

## 影响：这是"整体威胁压到 1/5"

100 血 = **50 颗心**，原版 HUD 每行 10 颗 ⇒ 占 5 行。

本模组的枪伤是**照 20 血玩家**调的（玩家版：弩 6 / 莫辛 8.5 / 加兰德 7.5 / AWM 12；怪物版再砍半）。
血量翻五倍之后，这些数字在体感上一起变弱五倍 —— 包括 `1.1.24` 刚做的怪物持枪。

**本轮有意不动枪械数值**：四把枪的伤害是玩家语义的一套体系（`FirePacket`/HUD/后坐力），
十字弩那条线还有「不许碰」的边界。若要把威胁重新拉回来，正确做法是在
`Config` 里加一个**全局伤害倍率**统一乘，而不是逐把枪去改。
