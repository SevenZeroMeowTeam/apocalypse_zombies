# 07 · 出货与版本管理

## 版号的唯一来源

`gradle.properties` 的 **`mod_version`** —— 它同时决定：jar 文件名、`src/main/resources/META-INF/mods.toml` 里的 `version`、
CI 打的 tag（`v<mod_version>`）、GitHub Release 的名字。改版号**只改这一处**。

`readme.md` 头表的"当前版本"（**开头那张表，约第 8 行**）与文末更新日志、`art/<功能>/DELIVERY.md` 的台账，
都是围绕这个版号的人工记录 —— **它们互不相干，改一个不会带上另一个**。

> ⚠ **头表是最容易漏的那一处**。1.1.50 → 1.1.55 连推五版时，每次都只写了更新日志段，
> 那张表一路停在 `1.1.49`，最后由用户自己在 GitHub 网页上改掉（提交 `e62a9a1 Update readme.md`）。
> **一次发版要动四处版本号**：`gradle.properties` → 根 `mod.toml` → `readme.md` 头表 →
> `readme.md` 新增版本段。查漏一行就够：`grep -n '当前版本' readme.md`。

## 出货脚本 `tools/_deploy_<ver>.py`

一版一个（已有 `_deploy_124.py` … `_deploy_140.py`）。它把整条链一次做完：

| 步 | 做什么 |
|---|---|
| 1 | **自升版号**（改 `gradle.properties` 的 `mod_version`） |
| 2 | 构建（`build` / `cleanJar`，必要时 `borrowedPack`） |
| 3 | **三向对账**：构建产物里的 `mods.toml`（源在 `src/main/resources/META-INF/mods.toml`）版本与依赖、资产清单、jar 内条目与源码一一对应 |
| 4 | **探锁部署**：确认游戏进程已退出再往 `mods/` 放包（避免放进去却在内存里跑旧包） |
| 5 | 把 `mods/` 里**其余模组逐个 md5** 比对，断言"原样在位"（没被误删误改） |
| 6 | 旧版本 jar 清理（同名模组两份 = 启动即崩） |

**判据只看退出码。** 输出里出现 `FAIL` / `✗` / `不通过` / `错误` / `不符` 即判负
（注意 `check_gun_resources.py` 用的是"全部通过"这种正向措辞，别按关键字反转判断）。

## 一次完整出货的动作序列

```bash
./gradlew --stop                                  # 清 daemon，避免行为诡异
python tools/_deploy_140.py                       # 自升版号 → 构建 → 对账 → 探锁部署
for s in tools/check_*.py; do python "$s" || echo "FAIL $s"; done   # 门禁全绿
# 完全退出游戏 → 重开 → 实机验证（含第三人称 / 换弹 / 开镜）
python tools/game_shot.py --title Minecraft       # 取证
```

然后更新文档与提交：

1. `art/<功能>/DELIVERY.md` —— 台账（资产、实测数字、真源脚本、门禁结果、不变量、踩坑）
2. `readme.md` —— 头表版本 + 更新日志条目
3. `git add -A && git commit` → `git push origin main`

推送后 CI 自动：刷新 **`preview` 预发布**（开发包 + clean 包）并发 **`v<版本>` 正式版**（只挂 clean 包）。
见 [08 CI 与 GitHub 发布](08-CI与发布.md)。

## 常踩的三个坑

1. **同名两份 jar** → 游戏启动即崩。备份一律改成非 `.jar` 后缀（`.jar.old.bak`）。
2. **版本号升了但 `mods/` 里旧包没删** → 实机测的还是旧行为（看起来像"改动没生效"）。
3. **忘记更新台账/readme** → 下一个接手的人（或下一轮的自己）无法判断"这个数字是量出来的还是估的"。
