# 07 · 出货与版本管理

## 版号的唯一来源

`gradle.properties` 的 **`mod_version`** —— 它同时决定：jar 文件名、`src/main/resources/META-INF/mods.toml` 里的 `version`、
CI 打的 tag（`v<mod_version>`）、GitHub Release 的名字。改版号**只改这一处**。

`readme.md` 头表的"当前版本"（**开头那张表，约第 8 行**）与文末更新日志、`art/<功能>/DELIVERY.md` 的台账，
都是围绕这个版号的人工记录 —— **它们互不相干，改一个不会带上另一个**。

> ⚠ **头表是最容易漏的那一处**。1.1.50 → 1.1.55 连推五版时，每次都只写了更新日志段，
> 那张表一路停在 `1.1.49`，最后由用户自己在 GitHub 网页上改掉（提交 `e62a9a1 Update readme.md`）。
> **一次发版要动四处版本号**：`gradle.properties` → 根 `mod.toml` → `readme.md` 头表 →
> `readme.md` 新增版本段。查漏一行就够：`grep -n '当前版本' readme.md`。

## 出货脚本 `tools/_deploy_<ver>.py`

一版一个（已有 `_deploy_124.py` … `_deploy_176.py`）。它把整条链一次做完：

| 步 | 做什么 |
|---|---|
| 1 | **自升版号**（改 `gradle.properties` 的 `mod_version`） |
| 2 | 构建（`build` / `cleanJar`，必要时 `borrowedPack`） |
| 3 | **三向对账**：构建产物里的 `mods.toml`（源在 `src/main/resources/META-INF/mods.toml`）版本与依赖、资产清单、jar 内条目与源码一一对应 |
| 4 | **探锁部署**：确认游戏进程已退出再往 `mods/` 放包（避免放进去却在内存里跑旧包） |
| 5 | 把 `mods/` 里**其余模组逐个 md5** 比对，断言"原样在位"（没被误删误改） |
| 6 | 旧版本 jar 清理（同名模组两份 = 启动即崩） |

**判据只看退出码。** 输出里出现 `FAIL` / `✗` / `不通过` / `错误` / `不符` 即判负
（注意 `check_gun_resources.py` 用的是"全部通过"这种正向措辞，别按关键字反转判断）。

## 一次完整出货的动作序列

```bash
./gradlew --stop                                  # 清 daemon，避免行为诡异
python tools/_deploy_173.py                       # 自升版号 → 构建 → 对账 → 探锁部署
for s in tools/check_*.py; do python "$s" || echo "FAIL $s"; done   # 门禁全绿
# 完全退出游戏 → 重开 → 实机验证（含第三人称 / 换弹 / 开镜）
python tools/game_shot.py --title Minecraft       # 取证
```

然后更新文档与提交：

1. `art/<功能>/DELIVERY.md` —— 台账（资产、实测数字、真源脚本、门禁结果、不变量、踩坑）
2. `readme.md` —— 头表版本 + 更新日志条目
3. `py tools/github_push.py -m "<提交信息>"` —— **一条命令跑完「扫描可用 GitHub IP → 写 hosts → 提交 → 推送」**。
   本机到 github.com 时通时不通，别裸敲 `git push`（实测会被 21 秒超时、`Connection was reset`、
   `! [rejected]` 三种方式顶回来）；脚本固定走 HTTP/1.1、逐条换 IP 试推（每条先用 `git ls-remote` 验通道），
   用法与三个坑见 `tools/github_push.py` 文件头。
   若远端有本地没有的提交，先 `git fetch origin main && git reset --soft origin/main` 把历史接到远端之上再推。

推送后 CI 自动：刷新 **`preview` 预发布**（开发包 + clean 包）并发 **`v<版本>` 正式版**（只挂 clean 包）。
见 [08 CI 与 GitHub 发布](08-CI与发布.md)。

## 常踩的三个坑

1. **同名两份 jar** → 游戏启动即崩。备份一律改成非 `.jar` 后缀（`.jar.old.bak`）。
2. **版本号升了但 `mods/` 里旧包没删** → 实机测的还是旧行为（看起来像"改动没生效"）。
3. **忘记更新台账/readme** → 下一个接手的人（或下一轮的自己）无法判断"这个数字是量出来的还是估的"。

## 1.1.84 · 本地 AI 助理换 LM Studio（OpenAI 兼容口）

- **换的是「线」，不是「脑子」**：`ai/OllamaWire` → `ai/LmStudioWire`。Ollama 的 `/api/chat`
  与 `options.num_ctx` / `format:"json"` / `think` 这几个字段 LM Studio **一个都不认**；
  照搬过去不是 400 就是被静默忽略 —— 其中 `format` 被忽略最阴：模型照旧回自由文本，
  锅却记在解析层头上。
- **实测撞出来的两个坑**（都钉进门禁了，别再撞第二遍）：
  1. `response_format` 只认 `json_schema` / `text`。把 Ollama 那份 `{"type":"json_object"}`
     原样发过去会 **HTTP 400**（原话：`'response_format.type' must be 'json_schema' or 'text'`）。
     现在发的是 strict 的 `json_schema`：五个键连类型、`count` 的 0–64 范围一起钉死。

     只读 `choices[0].message.content` 会白跑一轮（表现为「她想不出来」，其实是没拿到正文）。
     现在按 content → reasoning_content → `choices[0].text` 依次兜底。
- **不用手动加载模型**：`POST /v1/chat/completions` 里点名一个没加载的模型，LM Studio 会按需拉起来
  （首次几秒）—— 这也是 `timeout_ms` 默认从 20000 抬到 30000 的原因。
- **端点写法宽容**：`chatUrl()` 收「主机」/「主机 + `/v1`」/「整条 `/v1/chat/completions`」三种写法，

- **`json_schema` 开关**（默认 true）：万一某个版本 / 模型不收 json_schema，关掉即退回

## 1.1.83 · 挖掘数字（准星下方报数）

- **数字与框同源**：`renderCount` 用的是 `render()` 同一份缓存（同一个 `PlayerVeinMine.preview`
  结果），所以不会出现「框画了 12 个、数字说 11」。
- **框比数字少 1 个不是 bug**：瞄准的那一格由原版画黑框（我们故意不叠），但数字是这一下左键的
  **总账**，含它自己。两个都对，wiki/readme 里都写明了。
- **只报 2 格以上**：只砸一格时原版本来就是这样，没必要常驻一行字。
- **撞上限要说**：`count >= min(max_blocks, 64)` 时文案换成「会连挖 64 格（已到上限）」，
  否则你会以为眼前那一簇就这么大。
- **两个开关各管各的**：`highlight` / `count` 互不影响 —— 只要框、只要数字、都要、都不要都行。
- **顺手补了个谎**：1.1.82 的高亮在你**潜行**时还会照画一整簇，可实际上潜行只砸一格。
  根因是「潜行不连带」当时写在 `onBreak` 里、`preview` 不知道；现在这条判定收进 `preview`
  （服务端与客户端读同一份），潜行状态也进了客户端缓存键 → 蹲下立刻改画面。
- **文案走 lang**：`hud.apocalypse_zombies.vein_count` / `..._vein_count_capped`，中英各一份。

**怎么自测**：拿铁镐瞄铁矿脉（不按左键）→ 准星下方出「会连挖 N 格」，整簇同时冒青边；
**蹲下** → 数字和框一起消失（只砸一格）；把 `max_blocks` 改小（比如 8）再瞄一簇大的 →
文案变「已到上限」；`count=false` → 只剩框；`highlight=false, count=true` → 只剩数字。

## 1.1.82 · 玩家挖掘高亮（客户端描边）

## 1.1.90 —— 子弹穿叶 / 打碎玻璃 + 猫耳娘手持物品摆正

**怪物那发是实体子弹，插不上手**：它的命中判定在原版 `Projectile.tick()` 里（`ProjectileUtil.getHitResultOnMoveVector`
→ `level.clip`），拿不到钩子。所以换一条路：`BulletProjectile.onHitBlock` 先问 `BulletRay.resolveProjectileHit` ——
撞上叶子**不消散**，把实体挪到叶背出口接着飞；玻璃按同一份配置碎。规则与玩家那条同源，
配置也只有一份（`bullets.pass_leaves` / `bullets.break_glass` / `bullets.pass_glass`，默认 true / true / false）。
副作用是好的：`wallDistance` 变成「到第一个真挡路方块」的距离，躲在树后面的目标打得着了。

**二、她手里的东西。**1.1.80 给 `HeldItemLayer` 补了原版那两步基准旋转，但**多补了一步**。
原版实体渲染器在模型之外还压了一次 `scale(-1,-1,1)`（把模型里「Y 向下」翻成世界向上，顺带把模型 +X
映射到世界 -X），所以原版 `ItemInHandLayer` 那两步是写给**翻转前**那个空间的；她的 geo 是按**翻转之后**

—— 她的模型空间**本身就是已翻转空间**。记 F = `scale(-1,-1,1)` 代进去算：

```
F · XP(-90) · YP(180) ≡ XP(-90)        # 物品的三根基向量逐个验过
```

所以这里只需要 `XP -90°` 一次。多补的 `YP 180` 等于又套了一层 F：物品「面」朝下、自身右轴翻到她的左
—— 表现就是「倒着的、跟玩家拿反了、斧刃朝里」，三条症状同一条因（1.1.80 那次是「平物品立成牌子」的后续误判）。

**教训**：给「另一个坐标系」的模型补原版那几行时，先确认那次 `scale(-1,-1,1)` 到底在不在链上 ——
补错一步比不补更难看出来（1.1.80 看着「比原来对」，其实翻了一半）。

## 1.1.91 —— 爆炸弹只有特效没有伤害

**症状**：爆炸弹打中僵尸，粒子炸开、爆炸声都在，**目标一点血都不掉** —— 连子弹本身那 6 点引信伤害也没有。

**根因：一道只装了一半的闸。** `event/AmmoEffects` 里防递归的 `private static boolean detonating`
写了声明、`onLivingHurt` 开头也有 `if (detonating) return;`，但**全文件没有一处把它设成 `true`**。
爆炸用的伤害来源是 `player.damageSources().explosion(player, player)` —— 于是爆炸造成的每一次 `hurt`
都重新走进 `onLivingHurt`、重新满足「手里是爆炸弹」、再引爆一次：自己引爆自己，无限递归到
`StackOverflowError`。

**为什么偏偏表现成「特效有、伤害无」**：`detonate()` 一进门就发粒子与音效，而 Forge 的
`LivingHurtEvent` 触发点在伤害**真正应用之前** —— 递归把栈打爆时那一发伤害还没落地，于是
「命中伤害 + 范围伤害」一起作废。特效与伤害看着是两件事，其实是同一处的两端。

**修法**：补上合闸那一半（`if (detonating) return;` + `detonating = true;`），整段用 `try/finally` 收口。
**为什么必须 `finally` 而不是写在末尾**：闸是静态的，中途抛异常而不复位就会让它**永久锁死** ——
那时爆炸弹连特效都没有，比原 bug 更难查。

**别混淆的另一件事**：`SoldierZombie` 免疫 `DamageTypeTags.IS_EXPLOSION` 是**刻意的设定**（它就是要抗爆），
拿爆炸弹打它没伤害属于设计；普通僵尸才吃范围伤害。

口径一字未动：半径 `2.5`、中心 `14` 点、线性衰减、引信 `6` 点、只伤 `Enemy`、不破坏方块、玩家不在范围内。

### 同版第二件事：十字弩的弦（装弹后该拉满、发射后该平行）

**症状**：装完弹看着还是没上弦；右键瞄准时弩身与双手挡在准心环上。

**根因：静止类片段把弦写在了松弛位。** `crossbow_v2.py` 里 `static_idle` / `reload_tactical` /
`ADS_up` / `ADS_down` / `inspect` 全是 `bow_pose(p, 0.0)`（`ease` 0 = 弦在静止位）。于是装弹链
`draw`（拉弦上牙）→ `reload_tactical` 的第二步把刚拉满的弦放了回去；就算不动，切回 `static_idle`
也还是松弛位。**而弩的常态本来就是「已上弦待发」**：`getAmmo` 默认返回 `MAGAZINE_SIZE = 1`
（新弩到手就是上弦的），射空后 `inventoryTick` 立刻自动开始装弹 —— 玩家静止时看到的基本都是待发的弩。

**修法**：这五个片段改用新的模块常量 `SPANNED = 1.0`（弦挂在牙上）。真正经过松弛位的只剩
`draw` 的起点（空弦拉起）与 `shoot` 的终点（放弦弹回），它们各自用 `ease` 表达，不走这个常量。
`shoot` 末帧另钉一条判据：弦心离牙必须 ≥ 1u（放弦真做了），实测 `2.9774`。

**右键瞄准隐藏双手与武器**：`hidesModelWhileAimed()` 从 `false` 改为 `true`。旧注释的理由是
「透明镜是看穿的，弩该留在画面里」—— 漏算的是画面正中正好是准心环与十字，而满镜时弩身与双手
压在上面，玩家等于在透过自己的手套瞄。举镜过半（`SCOPE_HIDE_MODEL_AT`）把画面交给镜片后，
世界照样看得见：藏掉的是弩和手，不是那层镜。

**顺手修好一个一直没生效的门禁**：`check_crossbow_anim.py` 的弦缆运动学里 `bone_xform` 的缓存键
只有骨骼名、**不含时间**（`memo[name]`），而调用方按片段复用一个 `memo` 逐帧扫描 —— 整段动画的
每一次求值都拿回第一帧那个函数。「弦心最大距离」于是恒等于首帧值：`draw` 全程报 2.98u（看着像
"没拉弦"）、`shoot` 全程报 0.094u（看着像"没放弦"），这一段检查形同虚设。**修法**：缓存键改成
`(name, round(t, 6))`；修完第一次真正逐帧，`draw` 2.98→0.79→0.094、`shoot` 0.094→2.98 立刻显形。
判据也跟着换代：从「静止态弦心必须在牙前」改成「静止类片段不许离开牙」（`SPANNED_CLIPS` /
`SPANNED_TOL = 0.15`，满弦实测 0.0943u）。

**动画只重生成动画**：`crossbow_v2.py` 的 `write_all()` 会一口气重写 geo + 动画 + 贴图四份，但仓库里的
**geo 与贴图来自比该生成器更新的版本** —— 原样重跑会让它们倒退（实测 geo 与两张 png 的 md5 全变，
只有动画逐字节一致）。所以新增 `tools/crossbow_anim_only.py`：只跑 `build_anims()` → 过
`game_convention_anims` 取反层 → 只写那两个动画文件，绝不碰 geo/png。

出货脚本 `tools/_deploy_191.py`（由 `tools/_mk_deploy_191.py` 从 190 派生，断言段在 `tools/_assert_191.py`）。

## 1.1.99 —— 猫耳娘 AI：思考型模型把额度全想光了

**她刷在屏幕上的三种话**（`……我又想不明白了（没有 JSON）。` / `列表为空，无法执行任何任务。` /
`只能执行一次任务，制作石头。`）背后是**两个**根因，两个都在真机上量出来了。

### 一、`enable_thinking` 对 DeepSeek-R1 蒸馏系无效，`max_tokens` 被思考吃满

端点 = llama.cpp（`127.0.0.1:9931`）、模型 = `DeepSeek-R1-Distill-Qwen-1.5B-Q4_K_M`，实机回包原文：

```
finish_reason : "length"
completion_tokens : 100 / 100
content : ""
reasoning_content : "\n好，我来仔细分析一下这个问题。首先，玩家当前的状态是工种是FOLLOW，血量20/20…"
```

R1 蒸馏的思考是**模板级**的：请求里那个 `chat_template_kwargs.enable_thinking=false` 它不认
（`max_tokens=300` 时它能一路想到 299 个 token，`finish_reason` 直接 `length`）。
而旧版 `LmStudioWire` 的兜底恰好是「`content` 空 → 取 `reasoning_content`」——
**思考于是被当成正文**，思考文本里没有花括号，玩家屏幕上就得到「没有 JSON」。
这不是模型的错，是接线把「思考」与「答案」当成了同一个字段。

**修法一：先把她的答案头一个字符写好。** 在 messages 末尾追加一条内容就是一个 `{` 的 assistant 消息，
服务端把它当「已经开好的头」接着往下写。同一个 prompt、同一个模型实测：

| 路径 | max_tokens | 生成 token | 耗时 | `content` |
|---|---|---|---|---|
| 旧 | 300 | 299（截断） | 13.9 s | 空 |
| prefill | 300 | **36** | **1.6 s** | `{"reply":"好的，我这就去砍树。",…}` |

`continue_final_message` 这个 OpenAI 字段 llama.cpp 的 `/v1/chat/completions` **不认**（实测 HTTP 400），
所以走的是「末尾 assistant 消息 + 服务端默认的 add_generation_prompt」。LM Studio / llama.cpp 都收；
个别实现不收时 `LocalAiClient` **自动去掉这一条重来一轮**（开关 `ai.prefill_json`，默认 true）。

**修法二：解析层只认真答案。** `content` 是答案、`reasoning_content` 是思考。思考里恰好草拟过
一整段合法 JSON 时仍可拿来救命（旧行为不回归），但**思考本身绝不当回话端给玩家**。
挖不出 JSON 的理由也改成能动手的：「她的思考把 max_tokens 用光了，答案还没开始写就被截断 ——
把 `ai.max_tokens` 调大，或换一个不吐思考的模型」。取 JSON 的方式从「第一个 `{` 到最后那个 `}`」
改成**括号配平扫描**（字符串内与思考残渣里的花括号都跳过 —— 旧写法会把两段拼成一坨必失败的怪东西）。
`max_tokens` 从硬编码 300 变成配置（默认 **512**），`timeout_ms` 默认 30000 → **60000**
（思考型模型一轮真能想十几秒）。

### 二、「列表为空」的真身是候选表没载入

`CatGirlRecipeTable.ensureLoaded(server)` 的**唯一**调用点是 `/apocalypse catgirl recipes` 那条命令。
可玩家是**一进游戏就跟她说话**的 —— 表压根没载入，`CatGirlAiPrompt.candidates()` 于是恒空，
连兜底清单也被 `CatGirlRecipeTable.isPresent()` 挡在门外。候选空 → 小模型只能说
「列表为空，无法执行任何任务」（`只能执行一次任务，制作石头。` 同理，是它自由发挥）。

现在 `LocalAiClient.ask` 与 `CatGirlAiPrompt.candidates` 都会先 `ensureLoaded(server)`；
兜底清单也不再依赖配方表是否载入 —— 列表本来就不该是空的。
